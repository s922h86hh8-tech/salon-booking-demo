# 自店集客 → 自店予約 → 店舗一元管理 MVP-A

作成：2026年11月8日  
位置付け：**独立した架空データ専用の操作試作／採用・本番公開は未決定**。

## どこまで動くか

- `index.html`：店舗ページの設定、架空の集客ページ＋お客様の予約操作、店舗の予約管理の3画面。
- `core-v057.js`：`preview/v0.57-two-person-approval.html`に含まれる既存の第1 `<script>`（`DemoCore`）を**1文字も変更せずに複製**。既存のスタッフ・設備・コース・休憩・準備時間に基づく`Core.canBook`と`Core.book`を利用。
- `app.js`：3画面の操作と表示。全状態は**同じブラウザタブのメモリ**。別の端末やタブとは共有しない。
- `style.css`：スマートフォン向けレイアウト。
- テスト：`tests/marketing-booking-mvp-a.test.mjs`（8件）。既存予約エンジンの不変、偽DOMでのA→B→C予約、電話・店頭手入力、経路表示、キャンセル後の再判定、リセット、接続禁止を検証。

## 操作手順

1. 「01 店舗ページ設定」で**架空**の名称・紹介文を確認、編集し「プレビューに反映」。
2. 「02 お客様向け予約」でコース・希望スタッフ・開始時間・認知経路を選択して「模擬予約する」。対象日は固定の**2026年10月26日**。予約番号が発行されるが実予約ではない。
3. 「03 店舗の予約管理」で上記のWeb予約が表示されたことを確認。電話・店頭・外部媒体（手入力）からの架空の予約も同じ台帳に追加できる。
4. 模擬予約取消によって空き判定が更新される。既存の架空予約を含めた合計と自店Web経由件数を表示する。
5. リロードすると状態は消える。外部への保存・公開・通知・決済は行わない。

**予約経路**と**認知経路**は分けて記録し、「不明」を許容する。画面の予約件数は実来店・売上・新規獲得を示さない。既存デモに含まれる模擬予約3件も初期状態にある。

## 安全性と制約

- 実店舗名・住所・顧客名・電話番号、実際の予約情報を入れない。コード・検証URLは**公開GitHub Pages上で閲覧可能**であり、`noindex`はアクセス制限ではない。
- メモリのみ：`fetch`/`localStorage`/`indexedDB`/`XMLHttpRequest`/`WebSocket`は使用しない。CSPで`connect-src 'none'`、インラインスクリプト・外部ドメインの読み込みは行わない。
- 客側と管理側のタブが同じページにあるのは**架空デモの操作体験用**。実運用で共有してはならず、本番では管理画面に認証・店舗別認可が必要。
- 予約可能枠はデモ内部の`Core.canBook`で判定し、登録直前も再判定する。ただし**複数端末同時予約を防ぐトランザクションはない**。
- Google検索、Googleビジネスプロフィール、SNS、広告・外部予約媒体への接続は**一切ない**。HP生成は画面内プレビューであり、検索順位や集客は保証しない。
- 独自ドメイン、店舗写真のアップロード、曜日別営業時間、予約通知・本人確認、クーポン、売上会計・報酬・集客費分析への実連携は未実装。実Web予約として使わない。

## 開発順序案（採用未決定）

- **P0-B**：予約エンジンの規則をサーバー側でも再検証。共有DBの予約確定・変更・取消を、店舗IDとスタッフ・設備・時間の衝突条件を用いたトランザクションへ。二重タップ、重複リクエスト、別端末同時送信、タイムアウト後の再照会の試験が必要。
- **P0-C**：実際の本人認証・店舗別アクセス制御、予約本人確認（変更・取消）、監査履歴、バックアップと通知。v0.60の報酬訂正用ローカルAPIは**予約用APIではない**ため、そのままネット公開しない。
- **P1**：店舗ホームページの公開機能と独自予約URL、コース・スタッフ・営業時間の設定、計測URL・予約経路・認知経路の保持。店舗オーナーの承認下でGoogle予約リンクを設定する支援。
- **P1**：予約→実来店→会計→媒体費／実測作業時間の比較。仮定・自己申告・実測・不明を区別。新規顧客の純増は単なる予約件数では判定しない。
- **P2**：キャンセル待ち候補の同意・通知・枠確保、次回来店・紹介支援、AI告知案。外部送信・掲載・課金はオーナー承認必須。
