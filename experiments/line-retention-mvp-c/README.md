## 試す手順（すべて架空）

- 固定の「本日」を **2026-11-12**、「予約対象日」を **2026-11-13**として架空データを準備している。デモ閲覧時の実際の日付ではない。
- 「提案を準備」で予約前日のお客様Bに対するリマインド、過去の来店周期が28日間隔の架空のお客様Dへの再来店案内を作る。
- 別の「架空予約 #2 を取消」でキャンセル枠を発生させた後、同意・メニュー・時間帯等が一致する希望者への下書きを準備する。
- 「案内・予約状況」で、**下書き → 店舗オーナーの模擬承認 → 配信済みとして模擬記録（実送信なし） → 模擬予約成立**というステップを確認。
- 「通知の同意・設定」で、架空のお客様ごとに再来店案内／予約確認／キャンセル待ちを個別に許可・停止。停止した種類の未送信下書き・承認済み案内は無効化する。
- 「架空データを初期状態に戻す」を使うか再読み込みするとデモは初期化する。
- 個人情報・本物の店舗情報・LINEアカウント・アクセストークンを入力しない。

## 重要な仕様境界

- **実LINEメッセージは送れない**。SDK、Webhook、Messaging API、トークン、外部API通信なし。`connect-src 'none'`、`noindex`を指定。ただし公開GitHub PagesのURLはアクセス制限の代わりにはならない。
- 店舗側の「同意」ボタンは**架空データを切り替える模擬操作**であり、実顧客の配信同意を得た証拠にはならない。実運用では本人の明示的な許諾、日時・内容・証跡、いつでも停止できる方法が必要。
- 来店周期は架空の来店日間隔を14〜120日で検証し、単純平均から次回来店目安を算出。最低2件の訪問記録がない場合は「手動確認が必要」と扱う。AIが顧客心理や体調を推測しない。
- 再来店案内の候補作成は次回来店目安の10日前以降、かつ確定予約がない場合に限る。同一の案内の重複を防止し、最近の再案内への頻度制限を設けている。実時間のスケジューラーはなし。
- リマインドは店舗が承認した案内だけ模擬配信記録を付ける。停止同意を再確認する。配信済みという状態名も**デモ内部での模擬記録**で、LINE側で配信できた証拠ではない。
- キャンセル案内は既存エンジンの同意・希望メニュー・開始時間・担当希望を照合。提示は**枠の仮確保ではない**。受諾時に改めて予約可能か確認し、競合時には失敗して元データを保持する。
- お客様の来店周期通知と、キャンセル待ち・事務的な予約確認は**別の配信目的・同意**。一方の停止を、他方の同意に勝手に読み替えない。
- 模擬予約が成立した場合も顧客・売上・新規流入を意味しない。模擬経路`source=line`は予約発生テスト用のラベルであり、実LINEから予約されたことを示さない。
- 本番利用には顧客と店舗の本人確認、Webhook署名検証、トークンと秘密鍵の保護、店舗分離、送信同意・停止、送信料金・数量上限、配信失敗や再送による重複防止、予約枠の原子的確定、実店舗の設定と実会計への照合が必要。

## 計測を分ける

1. **事前試算**：再来店・キャンセル枠回収の見込み数 × 1件当たり限界利益 ＋ 作業削減時間 × 時間単価。ただし、費用の重複計上を避ける。
2. **配信実績**：実際の配信が成功した件数と費用。MVP-Cでは未実装。
3. **予約の実績**：予約確定、取消、実来店、売上・限界利益を別々に集計。MVP-Cでは模擬予約件数のみ。
4. **システムの効果**：「導入しなければ来なかったお客様」の純増や実際の時間削減は導入前後比較等の検証が必要。MVP-Cの模擬件数を成果として営業に使わない。
