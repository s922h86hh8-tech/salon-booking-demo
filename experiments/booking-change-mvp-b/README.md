# 店舗向けAI予約・会計・経営管理システム｜MVP-B 予約変更UI独立検証

作成：2026年11月10日  
位置付け：**架空データ専用／スマホ表示を意識した操作試作。正式採用・本番利用は未決定。**

## 目的

v0.63でローカルSQLite・localhost HTTP経由の**予約変更・日付移動を一括確定する処理**を検証した。MVP-Bでは、次の段階としてお客様がスマートフォンで「現在の予約→変更先選択→前後確認→確定／失敗」を直感的に操作できる画面を、**別フォルダの独立試作**として構築した。

**MVP-Bはv0.63の実APIに接続していない。** ブラウザ内に複製した架空予約情報だけを使い、見た目・案内・状態遷移を検証するもの。

## 試作画面での操作

1. 「お客様の予約変更」で架空の確定済み予約を表示。実氏名・電話番号などは入力しない。
2. 2026年10月26日または27日の**架空の体験日**、コース、担当希望、時刻を選択。既存v0.57の空き判定で、予約対象以外のスタッフ・ベッド・個室・休憩・施術前後の準備や清掃との競合を検査。
3. 「変更内容を確認する」で、変更前・希望する変更後を比較。**この画面ではまだ予約は変わらない。**
4. 「この内容で模擬変更を確定」を押すと、最新の架空予約を再評価。変更できた場合だけ、元予約に`cancellationReason='MOVE'`と移動先リンクを残し、新しい架空予約と架空の操作履歴を作る。
5. 希望先が埋まった場合には「希望枠に変更できませんでした」「元の予約は確定済みのまま」と表示。**元予約が消えない。**
6. 比較画面の「希望枠が先に埋まる場合を試す」では、別の架空予約を意図的に追加して競合を発生させ、失敗表示と元予約保持を検証できる。選択枠が元予約と重なり、別の架空予約を追加できない場合は競合の再現を実施しない。
7. 「店舗の予約一覧・履歴」では、変更元の取消済み原票、変更先の確定済み原票、架空の操作者・時刻・変更元／変更後のリンクを閲覧。
8. 「架空データを初期状態に戻す」でページ内の予約状態を初期化できる。画面再読み込みでも状態は消える。

## 安全・運用上の限界

- **本物のお客様の予約変更はできない。** 公開Webサイトからアクセスできても実運用の予約受付システムではない。
- `connect-src 'none'`で外部データ送信を禁止。ページ内だけの架空情報。パスワードや個人情報を入力する欄を設けない。`noindex`は検索インデックス抑止用であり、アクセス制限ではない。
- 顧客向け画面と店舗向け画面が同じページにあるのは**デモ限定**。本番では店舗側のログイン・権限・顧客本人による予約変更の証明が必要。
- 2つのモデル（日付）のメモリコピーを作り、予約ルールを再評価して、成功時だけコピーへ切り替える。**実データベースの`BEGIN IMMEDIATE`、共有保存、他端末の同時予約、実サーバー側のロックを画面で実行しているわけではない。**
- 変更によって顧客・予約経路・認知経路を保存するため、変更を新たな集客と誤計上しない。ただし集客・売上・来店の実測は行わない。
- 架空操作日時`2026-11-10T09:00:00.000Z`と操作者名は**テスト用固定値**。本物の認証結果・サーバーが採番する監査履歴ではない。
- 日付は2日固定。曜日別営業時間・休業・スタッフシフトの本番設定はない。予約変更キャンセル料、実通知、外部予約媒体連携、決済・会計、業務委託報酬連携も未実装。
- 実iPhone Safariでの視認性、操作感、スクリーンリーダー利用、サーバー上のアクセス制限は別途確認が必要。
