## 保存・予約確定の方式

1. 店舗・日付ごとに**架空の設定**（コース、スタッフ、対応メニュー、ベッド、個室、休憩、準備・清掃時間）をSQLiteに記録。設定内容は試作上固定。営業時間は既存デモの09:00〜18:00、15分単位。
2. 信頼されたテスト用セッション解決器から「架空のお客様ID／架空の管理スタッフID」を取得。これ自体は本人認証技術ではなく、本番利用不可。
3. **`BEGIN IMMEDIATE`** の書込みトランザクションを取得し、確定・取消されていない最新予約をSQLiteから取得。
4. 最新予約を用いて`Core.canBook`を評価。スタッフの施術＋準備時間、ベッド使用＋清掃時間、個室の競合、コース資格、休憩、営業時間をチェック。重なれば新たな予約を拒否。
5. 空いていれば予約レコード、二重実行防止用の操作キー、操作履歴を**1つのトランザクション**で追記。書込みに一箇所でも失敗すれば全体ロールバック。
6. 予約取消時は元の予約を消したり上書きせず、取消履歴と監査履歴を追記。次の予約判定からは取消済み枠を空きとして扱う。
7. 二重タップ・再送は店舗・本人・操作種別・再送キーで識別。同一内容の再送は既存結果を返し、同じキーで内容を変更すれば拒否。

### データ構造

| テーブル | 内容 |
|---|---|
| `stores` | 架空の店舗ID |
| `staff_memberships` | 店舗ごとの模擬スタッフ所属・役割・停止状態 |
| `day_configurations` | 店舗・日付ごとに固定した架空のコース／設備／スタッフの条件 |
| `booking_records` | 確定時のコース、担当、設備、開始分、認知経路、予約経路、模擬お客様ID、日時 |
| `booking_cancellations` | 元予約に紐づく取消事実と操作ID・日時 |
| `booking_commands` | 再送キー、操作内容の指紋、対象予約ID |
| `booking_audit_events` | 確定・取消の追記専用監査履歴、記録順の連番 |

これらは試作上、店舗IDを含む複合キーと外部キーで関連付ける。元の予約・取消・監査履歴には更新・削除禁止トリガーを設ける。**DB管理者が強制的に改変するリスクまで防止しているわけではない。**

## 自動テストで確認できたこと

`tests/local-booking-v061.test.mjs`に14件追加。

- 既存`Core.canBook`の採用。
- 同一再送キーで1件のみ確定、異なる内容でのキー再使用を拒否。
- 別のお客様の同じ時間・同じ担当と設備の重複を拒否。
- 担当スタッフの準備、ベッド清掃、個室使用、休憩による衝突の判定。
- 別店舗・別日付の予約を独立した枠として扱う。
- 模擬本人の予約だけ閲覧・取消でき、別の模擬お客様や別店舗スタッフを拒否。
- 店舗側の電話などの手入力経路を区別し、お客様が予約経路を偽装できない設計。
- 取消後に元予約の履歴を残しながら再予約可能。
- 不正日付、存在しないコース・担当・設備、未認証・不正な入力を拒否。
- 予約または取消の監査書込みに失敗したら変更をロールバック。
- SQLiteファイルを閉じて開き直しても予約が残り、同じ時間への二重登録を拒否。
- **二つの独立Workerスレッド**から同一ファイル・同一枠へ同時申込み。実測テストで**一方だけ成功、一方は`SLOT_UNAVAILABLE`**、記録が1件のみ。

## 制限・注意事項

- **実際のお客様のスマホから利用できる状態ではない。** ローカルSQLiteにアクセスするNode用試作で、公開API・本番認証・iPhone Safari連携は未実装。
- SQLite書込みトランザクションを使用した試作範囲では、競合を防止できた。公開サーバー・分散構成・高負荷運用で同じ性質が維持される保証はまだない。
- 正式な店舗予約データの取り込み、本人確認・予約所有者の証明、通知、予約変更の原子的処理、営業日・営業時間の変更、複数スタッフ／店舗の実運用権限、バックアップ、復元、監査改ざん防止は未実装。
- キャンセル後の再予約は手動の独立操作。**予約変更（旧予約取消＋新枠確定を一括コミット）はまだ未実装**。
- 外部予約媒体、Google、LINE等の実連携はなし。外部媒体予約を自動的に取り込む機能もない。
- `unsafeDbForTests`は架空初期データ登録・障害試験に限って公開されたテスト専用入口であり、本番システムのAPIに出してはならない。
- 現段階で実店舗名・実顧客名・電話番号・住所・本物の予約を登録しない。

## 今後の推奨工程

1. **ローカル限定の予約API試作**：予約の空き照会／申込／取消／予約表取得をテスト用の別プロセスから呼び、同じSQLite台帳の状態を検証する。
2. **予約変更の原子的処理**：取消と新枠確定を一括処理し、片方が失敗した場合に元の予約を残す。二重操作・キャンセル待ち競合などを試験。
3. **実際の認証・店舗ごとのアクセス権・予約本人確認**、API接続と永続データ管理、バックアップ・監査・通知、iPhone Safariの操作実験。
4. それらが安全に完了した後に初めて、独立した顧客予約ページと管理画面を共通バックエンドへ接続。実データを扱う前に個人情報・外部媒体規約の監査を行う。
