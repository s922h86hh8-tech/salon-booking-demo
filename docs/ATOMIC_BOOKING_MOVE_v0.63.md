## 1. 目的

MVP-Aの「集客ページ → 自店予約 → 店舗の共通予約表」に必要な次の課題として、**予約変更・日付移動に失敗しても、変更前の予約が消えないこと**を検証する。

具体例：2026年10月26日14時の予約を15時へ変更しようとして、15時が埋まっている場合には14時の元予約を保持。空いている場合には元予約・新しい予約・変更先・担当者・操作日時・操作結果を関連付けて記録する。試作の時間・日付・担当者は架空。

## 3. 予約変更処理（模擬）の動作

1. テスト用セッション情報から架空の操作主体を識別し、予約が同じ店舗にあるか確認する。お客様は自分の予約のみ、店舗スタッフは自分の所属店舗内の予約のみ変更できる。
2. `BEGIN IMMEDIATE`を取得した後、元予約が存在し、取消・移動済みでないことを確認する。
3. 変更希望の店舗・日付・コース・担当者・ベッド・時間を検証する。元予約の予約経路・認知経路・所有者IDを保持し、**予約変更を新規集客として数えない**。
4. 最新の予約状況をSQLiteから取得。変更する元予約だけを空き判定から除外し、それ以外の予約に対して**既存v0.57の`DemoCore.canBook`**で担当者・個室・ベッド・準備／清掃時間・休憩などの競合を再判定。
5. 変更先が埋まっている／日付が未設定などの場合、**元予約を変更せず処理終了**。
6. 変更先が空いていれば、元予約の「移動として取消」のイベント、新しい予約原票、旧→新のリンク、再送防止キー、両予約の操作監査イベントを**ひとつのDBトランザクションで追記**する。どれかが失敗した場合は一括`ROLLBACK`。
7. 移動後も旧予約は削除せず、`cancellation_reason='MOVE'`と`moved_to_booking_id`で変更先を確認可能。さらに変更した場合も、旧→中間→最新の連鎖として履歴が残る。
8. 同じ変更リクエストを同じキーで再送した場合は新しい予約を作らず、元の結果を返す。同じキーで異なる内容を送った場合は拒否。

## 4. ローカル限定のHTTP試験

- `POST /v0.63/stores/{storeId}/bookings/{bookingId}/move`に、変更先の日付・コース・担当・ベッド・開始時刻、操作再送キーを渡す。
- 接続先・接続元は127.0.0.1のみに限定。外部公開・スマートフォンからのアクセスは**しない**。
- テスト内で生成した模擬Bearerトークンから架空の人物へ内部的に対応付ける。実ログイン、招待、パスキー、MFA、セッション失効・認可済み本人確認ではない。
- 操作対象の店舗ID・本人ID・予約ID・予約経路をHTTPボディで偽装できないよう、ボディに許可した変更先項目以外が含まれていれば拒否する。
- HTTP経由でも競合時は409として拒否し、DBの元予約は残る。監査書込み失敗時は内部SQL情報を返さず500とし、元の予約を保持する。

## 5. 監査・テスト結果

2026-11-09 GitHub Actions `42621083231`：**205件中205件合格・失敗0件**。v0.62時点の174件に、v0.63ローカル13件・HTTP18件を追加。

検証した主な条件：

- 同一日・別日への変更成功、元予約と変更先の一意リンク、担当者・時刻・順序を追記する履歴。
- 希望先が予約済み・日付未設定の際には元予約が残る。
- 他人の予約・所属外店舗・取消後の予約への変更を拒否。
- 同一操作再送で予約の二重作成を拒否し、同一キーで異なる変更は競合扱い。
- 変更後も顧客所有者ID、予約経路、認知経路を維持。
- 監査保存障害で、旧予約の取消、新予約、リンク、再送記録までまとめて取り消す。
- **独立Workerスレッド二つによる同一移動先の競合**で、変更成功1件・拒否1件。拒否された元予約は有効なまま。SQLiteには既存予約2件と変更後の追加予約1件が残る。
- DBを閉じて開き直しても元→新の履歴が保持される。
- 過去のv0.61〜v0.62のテストはそのまま継続合格。

## 7. 次に安全につなぐ工程

まず予約変更の**3画面操作UX**（お客様が日付・コース・担当・時間を選び直し、失敗時は元の予約を維持した旨を明確に表示）を**架空データだけの独立版**で検証。後に真正な認証と本番DB／APIが整った段階で、顧客と店舗の操作画面を分離し安全に接続する。

画面の機能検証が進んでも、実店舗の予約情報を入力する許可にはならない。公開GitHub Pagesはアクセス制限の代わりにはならない。
