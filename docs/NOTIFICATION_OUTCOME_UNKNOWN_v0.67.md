## 目的と背景

v0.66ではローカルSQLiteに予約同意・通知・送信予定・リース・再試行を保存できた。しかし、**外部サービスが通知を受け付けた直後に通信が切れた場合、受け付けられたかどうか不明なまま再送すると二重配信になる**という問題を扱っていなかった。

v0.67では、外部の送信処理に入る前にSQLiteへ`OUTCOME_UNKNOWN`（結果不明）を記録し、**結果が確認されるまで自動再試行しない安全側の制御**を独立検証する。これは将来の実送信に備えた設計実験であり、**模擬送信先も実通信も存在しない**。

## 状態遷移と安全策

1. 既存の予約・同意・店舗承認を確認した通知ジョブを`WAITING`として登録。実際にはLINEへ送らない。
2. 期限付きリースを一人の模擬ワーカーが取得して`CLAIMED`になる。
3. `beginUncertainHandoff`：予定時刻、リース所有者とトークン、同意、予約の有効性、上限を確認したうえで、**送信結果が不明になり得る境界を`OUTCOME_UNKNOWN`として保存**。一意な`handoffId`を発行しリースを外す。これだけでは送信しない。
4. `OUTCOME_UNKNOWN`中は、既存の`claim`、`reconcile`、リース期限切れ、ジョブ有効期限切れによる自動再取得を許可しない。**時間が経過しても無断で再送しない**。
5. `resolveUncertain`：架空のオーナー/マネージャーが、模擬調査結果として`MOCK_ACCEPTED`または`MOCK_NOT_ACCEPTED`を明示記録する。違う店舗・権限のないスタッフ・顧客本人による決定は拒否。
6. `MOCK_ACCEPTED`：`SIMULATED_ONLY`をSQLiteに追記して`SIMULATED`とする。後から同意が撤回されていても、**過去の模擬受付が確認できたという履歴**として残し、再送はしない。
7. `MOCK_NOT_ACCEPTED`：原則`DEAD`として停止。店舗オーナーが`retryApproved=true`を明示し、試行回数・有効期限・最新の同意・予約条件をすべて満たす場合に限り、60秒後の`RETRY`を許可する。
8. 模擬調査結果を同じ`handoffId`で再送しても、結果が同じなら重複確定を防ぐ。違う結果なら`FINDING_CONFLICT`。古い試行IDで新しい試行を確定できない。
9. 模擬配信数の上限は、**結果不明の引渡し開始も1件として保守的に計数**する。結果判明前に上限を超えて新たな送信処理を増やさない。
10. 模擬受付イベント・キュー状態・監査イベントは**単一SQLiteトランザクション**で更新する。監査障害があればその状態更新もロールバック。

### 例：実際に起き得る通信断（設計上の想定）

- LINE側へ送信リクエストを出す直前に`OUTCOME_UNKNOWN`を保存していたとする。
- その後、実際には受け付けられたかもしれないが、送信元は応答を受け取れず停止する。
- 再起動した処理が`OUTCOME_UNKNOWN`を読み取る。
- **自動的には再送しない。**
- 必要な調査・照合で受付済みと確認できれば終了。未受付と確認できれば最新の同意・予約を確認し、店舗側の許可後にだけ再試行を検討する。
- 調査方法がない場合は結果不明のまま保留する。

**重要：上記は実LINEへの送信処理を実装したものではなく、将来の安全設計を模擬したもの。** LINE側で受付済みかを照会できる仕組みの有無・手順は本工程で確認していない。

## テストと確認結果

GitHub Actions run `43218093087`：**304件中304件合格、失敗0件**。これまでの285件にv0.67の19件を追加。

v0.67専用テストの主な検証：
- 試験用モードでしか起動できない
- v0.66スキーマを自動移行せず拒否
- `OUTCOME_UNKNOWN`へ移行しても実送信0件
- リース期限切れ・ジョブ期限切れ・再起動後も結果不明を自動再送しない
- 古いリース・試行IDでの確定を拒否
- 模擬受付済みを一度だけ履歴登録し、同一結果の再送で重複させない
- 模擬未受付の場合、店舗側の明示許可なしでは再試行しない
- 最新の同意・予約の条件を満たさない場合は、許可があっても再試行しない
- 同意撤回後でも、**送ることなく**後から判明した模擬受付の履歴は別途保存する
- 模擬上限に結果不明の処理開始を含める
- 監査障害時に結果不明への切替／解決を半端に確定させない
- 保存済みSQLiteを閉じて開き直した後も`OUTCOME_UNKNOWN`が維持される

初回は同意撤回後の停止履歴と後から判明した受付結果の両方を数えるテストで、期待した履歴件数が1件少なかった。**両方の履歴を残す設計を維持**し、試験期待値を修正して全件合格した。
