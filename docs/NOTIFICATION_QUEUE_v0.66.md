## ジョブ状態

| 状態 | 意味 |
|---|---|
| `WAITING` | 店舗承認済みの架空案内を、指定時刻まで待機 |
| `CLAIMED` | 一人の試験用ワーカーが期限付きの処理権限（リース）を取得 |
| `RETRY` | 模擬失敗。一定時間後に再試行可能 |
| `SIMULATED` | SQLite内の`SIMULATED_ONLY`イベントを一度だけ追記した。**実際の配信ではない** |
| `SUPPRESSED` | 同意撤回、予約変更・取消、枠の消失などで停止 |
| `DEAD` | 期限切れ、再試行上限、模擬配信枠の超過で終了 |

## 動作と安全上の設計

1. `enqueue`：架空の店舗オーナー／マネージャー権限、既存案内の店舗承認、対象者の同意、現在の予約状態、予定時刻・有効期限を検証して、1件の待機ジョブを追加。同じ下書きと同じ期間を重複登録しない。
2. `claim`：SQLiteの`BEGIN IMMEDIATE`内で、処理対象・期限・承認・同意・予約の有効性を再評価し、同一ジョブを**一度に一つのワーカーだけ**へ貸し出す。リースは期限付きのランダムなトークンを使い、試験時のワーカーを識別する。
3. `complete`：正しいワーカーと有効なリーストークンを確認。直前に再度同意と最新の予約を検証。模擬成功なら`notification_events`と`notification_queue_events`を同じSQLiteトランザクションで更新する。片方で失敗すれば全体ロールバック。
4. `SIMULATE_FAILURE`：配信処理が失敗したと**模擬記録するだけ**。1回目の待機60秒、2回目120秒のように待機時間を延ばす。最大試行回数と有効期限で停止。
5. リース期限が切れた処理を、別ワーカーが取得して再試行可能。古いワーカーのトークンでは確定できない。実際の外部配信が実行されたかどうかを判定する仕組みではない。
6. `reconcile`：期限切れ、承認・同意の撤回、対象予約の変更・取消、すでに確定予約があること、キャンセル枠の消失などを確認し、不要なジョブを停止として記録。
7. 店舗と顧客の架空の権限を分離し、他店舗の担当者が閲覧・操作できないようにする。実際の本人認証ではない。
8. **このモジュールにはネットワーク通信やLINEへの送信APIがない。** `SIMULATED_ONLY`は受信・開封・クリック・予約・来店を証明しない。

## 検証結果

GitHub Actions run `43177755468`：**285件中285件合格・失敗0件**。従来の261件にv0.66専用24件を追加。

重要な検証：
- 送信予定時刻前の取得拒否と期限切れの停止
- 同一内容の再登録は重複させず、異なる予定での再登録は競合として拒否
- 承認前の送信予定登録を拒否
- 正しい試験用リースの発行と、リース期限切れ・旧トークンによる確定拒否
- 試験失敗によるバックオフ再試行、試行回数上限による停止
- 同意撤回があれば、待機中も処理取得済みも停止
- 予約取消・日付や時間の変更による無効化
- 日別の模擬配信件数上限
- イベント履歴保存時の障害ではジョブや模擬送信が半端に確定しない
- データベースファイルを閉じて再度開いた後もジョブの状態を保持
- **独立Workerスレッド2本・SQLite接続2本が同じ通知ジョブを同時取得したとき、取得成功1本・取得なし1本**
- 処理中断後に別のSQLite接続から期限切れリースを回収し、古いトークンでは確定できない
- 監査イベントに対する通常のUPDATE／DELETEをトリガーで拒否

## 実運用にはまだ不足すること

- **LINEの実送信、Messaging API、Webhook、配信結果との照合は未実装**。模擬成功を配信成功と呼ばない。
- 実送信では、プロバイダーが受け付けた直後にサーバーが止まるケースがあるため、単なる再試行では二重送信の危険がある。**今回のSQLite上の一回だけの模擬記録は、外部送信の厳密な一回保証ではない**。将来は外部サービス側の冪等性・応答照合・送信状態不明の扱いを設計・検証する必要がある。
- 本当の顧客／店舗本人確認、同意取得時の正式な証跡、LINEアカウントの本人紐付け、連絡先の保存・保護は未実装。
- 本番向けの予約・通知一体型API、実店舗のカレンダー、曜日別の営業時間・休暇・スタッフ権限管理、確実なバックアップ／復元が未完成。
- 日付判定は**試験時計のUTC日付**に基づく。実際の日本の予約ではAsia/Tokyoの営業日・時刻・サマータイムを含む時間帯設計が必要。
- 多数のワーカー、高負荷、通信断、複数サーバー、障害監視・運用者への警告、実配信費用、月次上限、顧客の配信停止反映時間、iPhone Safari実機操作は未検証。
- 顧客の実来店・会計・スタッフ報酬、実売上・限界利益・業務削減時間への計測連携は未実装。
- 本試作は自動でリアルタイムに動くスケジューラーではない。時刻を進めるテストと明示的な`claim`操作で処理を検証している。

## 次の工程案

1. **ローカルでの送信結果が不明なケースと、再試行の運用制御**：プロバイダー応答の有無を模擬し、「配信済み」「未配信」「状態不明」を区別。費用・過剰送信防止の仕組みを追加し、誤配信を監査。
2. **本人認証・安全な予約照会と通知先の紐付け**：店舗オーナーとお客様の本人確認、配信目的別の同意証跡、予約変更時の権限管理。
3. **お客様向け画面と店舗管理画面の分離接続**：架空のMVP-A/B/Cではなく、認証された予約・同意・通知の共通DBから操作できることを検証。
4. 実LINE連携は公式規約、費用・月間配信数・安全性を確認し、実際のオーナー承認を得てから限定検証。

**現段階の成果はSQLiteキューのローカル障害復旧試験までであり、LINEサービスや実店舗へは何も送信していない。**
