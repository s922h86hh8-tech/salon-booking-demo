# 店舗向けAI予約・会計・経営管理システム v0.60 — ローカルAPI・認証境界・訂正履歴 試作報告

作成日：2026-11-03  
状態：**ローカル限定・架空データ限定の技術検証**。実店舗・実顧客・実スタッフの本番システムではない。

## 1. 目的

v0.59で検証したSQLiteの訂正申請→別担当承認→金額反映→監査履歴の流れを、ネットワーク越しの実際のHTTPリクエストで試験する。ただし外部公開はせず、**127.0.0.1のローカルループバック上だけ**にサーバーを立てる。ログイン基盤を新設したかのように誤認させない。

今回作成したものは、将来の実認証基盤と本番サーバーを選ぶ前に、APIとデータベースの境界を試すための部品である。

## 3. APIの試験範囲

すべてローカル専用。URLの`{storeId}`は対象を示すだけであり、権限そのものは必ずSQLiteの店舗所属・役割から判断する。

| メソッドと経路 | 試験内容 |
|---|---|
| `POST /v0.60/stores/{storeId}/correction-requests` | 訂正申請。金額には未反映。再送キーで二重登録防止 |
| `POST /v0.60/stores/{storeId}/correction-requests/{requestId}/decision` | 別人による承認・差戻し。承認時のみ一括反映 |
| `GET /v0.60/stores/{storeId}/staff/{staffId}/statements` | セラピスト本人または同店管理者による報酬明細閲覧 |
| `GET /v0.60/stores/{storeId}/audit-events` | 同店の権限を持つ管理者による監査閲覧 |

テストでは各担当者用の乱数トークンを作り、**テストプロセス内部の対応表で架空の本人IDに変換**する。実際のログイン・パスワード検証・JWT署名検証・トークン失効管理・MFAではない。テストトークンはリポジトリに固定値で保存しない。

入力はJSONのみに限定し、本文最大16KiB、未知のパラメータを拒否する。HTTPの要求先と接続元はループバックのみ、他のホスト・Origin・Cookieを拒否し、CORS許可ヘッダーを付けない。レスポンスは非キャッシュ、内部SQLエラーや秘密情報を返信しない。**この制約を本番インターネットAPIのセキュリティ対策としてそのまま流用しない。**

## 4. 金銭訂正と監査の一貫性

1. 本人IDは端末からの名前ではなく、テスト用トークンに対応するサーバー側のセッションとDBのユーザー情報で確認。
2. 申請時に元の締め額、原票額、支払額、版番号を固定。申請時点では金額変更なし。
3. 別ユーザーIDの承認担当が、現在値との一致を確認。本人自己承認、停止した所属、別店舗の処理は拒否。
4. 承認した場合のみ、別記録の調整額と月次派生額の版更新を行う。同じSQLiteトランザクションに判断・監査イベントも含める。監査の保存が失敗したら全体ロールバック。
5. `audit_events`は`event_seq`（保存順を示すDB連番）で順序を記録し、時刻が同じ場合の逆順表示を防ぐ。
6. `audit_events.actor_name_snapshot`は、**監査記録時にDB上の担当者名を読み取って保存**する。後からユーザーの表示名が変更されても、当時の履歴が変わらない。担当者IDと時刻も保管。ブラウザから送信した名前は採用しない。
7. v0.59の既存SQLiteファイルをv0.60に黙って流用しない。必要なカラムがない旧スキーマはエラーとして拒否し、移行ツールは今後別に実装する。

## 5. テストで確認したこと

- ループバック限定起動、認証ヘッダーの不足・不正値拒否、別店舗・他スタッフの明細アクセス拒否。
- 申請・別人承認・報酬額変更・監査がHTTP経路で一貫して動くこと。
- 申請の再送キーでの二重登録防止、二重承認拒否、申請後の支払記録変更による失効。
- 監査保存失敗での一括ロールバック（訂正決定・調整額・月次状態を戻す）。
- HTTPレスポンスの非キャッシュ、未知フィールド・不正JSON・大きすぎる本文・不正Content-Type・Origin送信の拒否。
- 所属停止が既存のテスト用トークンにも直ちに反映されること。
- 旧v0.59スキーマの流用拒否、担当者名の変更後も以前の監査記録が保持されること。
- v0.36および各旧HTMLの予約コアや画面は変更していない。

## 6. 本番構成の候補（採用決定前）

**第一候補として調査する構成**：Supabase Auth ＋ PostgreSQL ＋ Row Level Security（RLS）＋サーバー側の訂正・承認トランザクション。

公式ドキュメント：
- 認証／セッション：https://supabase.com/docs/guides/auth
- サーバー側の認証：https://supabase.com/docs/guides/auth/server-side/creating-a-client
- PostgreSQL RLSとアクセス権：https://supabase.com/docs/guides/database/postgres/row-level-security
- サーバー用SDKの選択：https://supabase.com/docs/guides/auth/choosing-a-server-package

候補理由：サインインの本人IDと行単位の店舗アクセス制御を組み合わせる選択肢があり、ブラウザの自己申告を権限として信用しない設計と合わせやすい。ただしRLSはテーブル権限とポリシーを両方正しく設定・テストする必要がある。秘密鍵をブラウザへ置かない。承認判断・金額調整・監査保存は、サーバーやDBの**一括処理**で実装する。認証プロバイダーや運用プラン、費用、リージョン、バックアップと法令上の保存要件は未選定であり、**Supabase導入を正式決定したものではない**。
