## 確認した機能

| 機能 | 現在の状態 |
|---|---|
| 同意履歴の保存 | 架空のお客様が目的別に同意・撤回を行う試験。日時・人物IDを追記専用履歴に保存 |
| 予約リマインド | 翌日の有効な予約と予約所有者ID・本人同意が一致した場合に下書きを作成 |
| 来店周期案内 | 架空の来店記録の単純平均から日数を計算。履歴不足、すでに予約済み、対象期間外を拒否 |
| キャンセル待ち案内 | 同意・希望日時・コース・担当・元予約の取消状態・空き枠を確認して下書きを作成 |
| 店舗側の承認 | 店舗の架空オーナーまたはマネージャーだけが承認可能 |
| 配信記録 | **`SIMULATED_ONLY`という模擬イベントのみ**。実際の送信は0件 |
| 配信停止 | 同意撤回後、まだ配信していない下書き・承認済みの案内を`SUPPRESSED`として追記。元履歴は保持 |
| 二重実行防止 | 送信状態イベントの一意制約、同じ内容の再送、通知周期の重複検出 |
| 架空の日別配信上限 | 同じ店舗の模擬配信イベント件数に仮の上限を設け、超過を拒否 |
| 予約変更・取消の照合 | 下書き作成・承認・模擬配信直前に最新の予約台帳を読み直し、取消済み・変更元・既予約を拒否 |

## 特に重要な安全確認

**1. 同意は店舗が代わりに作成しない。**  
試作上は本人の架空セッションでのみ同意イベントを作成できる。店舗担当者は顧客になりすまして同意を追加できない。これはあくまで模擬本人識別であり、本物の本人確認や適法な同意の証拠ではない。

**2. LINEに送らない。**  
`simulateDispatch`はSQLite内に`SIMULATED_ONLY`を記録するだけ。LINE公式アカウント、Messaging API、Webhook、電話・メールへの連絡、広告出稿、決済、課金は一切実行しない。

**3. 送る直前にも予約と同意を検査する。**  
予約変更によって旧予約が無効になった場合、予約取消された場合、既に再予約されている場合、希望枠が他のお客様に埋まった場合は模擬配信を拒否。元データは削除しない。

**4. 既存の予約確定ロジックは変更しない。**  
独立した通知モジュールからv0.63の予約・取消・空き照会を参照する。予約の二重確定を防ぐv0.63の`BEGIN IMMEDIATE`や予約変更トランザクションには変更なし。

**5. 店舗間のデータは別に扱う。**  
通知は`store_id`を含むキーと店舗権限に基づいて読み書きする。別店舗に属するスタッフの閲覧は禁止。模擬顧客は自分の通知だけを閲覧できる。

## 監査・テスト

実行：
```bash
node --test tests/notification-ledger-v065.test.mjs
node --test tests/*.test.mjs
```

GitHub Actions `43145173935`：**既存238件＋v0.65の23件＝261件合格、失敗0件**。

主な検証：
- 予約台帳を壊さず通知テーブルを追加・再オープンできる
- 目的別の同意・撤回と追記専用記録
- 予約本人と翌日の有効予約の一致
- 同じ通知再送キーや周期での重複拒否
- オーナー未承認・受付担当者からの承認拒否
- 取消・移動済み予約に対するリマインド拒否
- 来店履歴不足と既予約による再案内抑止
- キャンセル待ち希望条件と空き枠の再検証
- 模擬の1日送信件数上限
- 承認後に同意撤回した案内も停止履歴へ移行
- DBの履歴改ざんを通常のUPDATE/DELETEで防止
- 監査イベント挿入失敗で下書き作成全体をロールバック
- **送信成功や実来店・実売上を偽って表示しない**
