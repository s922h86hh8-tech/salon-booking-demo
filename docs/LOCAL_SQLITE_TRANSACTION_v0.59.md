# 店舗予約・会計・経営管理システム v0.59 — ローカルSQLite保存・承認処理 試作結果

作成日：2026年11月3日  
対象：架空データのみ／設計とローカル試験。**本番システムではない。**

## 達成したこと

v0.58の「サーバーが本人・所属・権限を確認する」という仕様を、ローカルに動くSQLite試作へ接続した。対象は月次締め後の業務委託報酬訂正の申請・承認・履歴に限定する。

1. **店舗別保存**：`stores`、`users`、`store_memberships`、`monthly_closings`、`earnings_source_lines`、`payment_records`、`closing_projections`、`correction_requests`、`correction_decisions`、`correction_adjustments`、`audit_events`をSQLiteで保持。店舗IDとレコードIDを組み合わせた複合外部キーで店舗の取り違えを防ぐ試作。
2. **認証と権限の境界**：テストで用意した`resolveSession`から本人IDを受け取り、SQLite上のユーザーと店舗所属・役割・セラピスト対応IDを照合。v0.58の権限判定コードを呼び出す。**本当のログイン認証はまだない。画面側からの任意の名前・役割は信用しない想定。**
3. **申請時は金額不変**：締め・原票を読み直して調整の妥当性を確認し、申請者ID・時刻・変更希望額・理由・原票／月次額と支払額の版・スナップショットを登録する。訂正申請と操作監査イベントを同時に保存する。
4. **別人承認のみ反映**：申請者自身の承認を拒否。承認直前に原票額・月次額・版番号・既支払額を読み直す。変わっていた場合は`STALE`で承認済み調整を作らず、再申請扱い。差戻しも金額不変。
5. **DBトランザクション**：`BEGIN IMMEDIATE`から判断・調整・月次派生額・監査イベントを同一トランザクション内で書き込み、すべて成功なら`COMMIT`、途中失敗なら`ROLLBACK`。監査書込み失敗で金額が変わらないことをテストした。
6. **二重操作対策**：申請にクライアント再送用キーを設定し、同じ人・店舗・キーの同一申請は既存申請を返す。違う内容のキー再利用は拒否。判断は1申請につき1回に限定し、SQL側でも承認前の調整・自己承認を拒否するトリガーを設けた。
7. **訂正前記録の保護**：元締め、報酬原票、支払記録、申請、判断、調整、監査イベントに更新・削除拒否トリガーを付与。月次派生額だけ版付きで更新する。**DB管理者によるトリガー解除・ファイル改変を防げる仕組みではない**。
8. **ファイルの継続性**：テスト用の架空SQLiteファイルを閉じ、再度開いてから調整後の金額・監査記録・二重承認防止が維持されることを確認。これはローカルファイルの再起動試験であり、サーバーDBの運用確認ではない。

## 開発者向けの再現方法

Node.js 22の`node:sqlite`を使用（この環境では実験的機能）。ルートで以下を実行：

```bash
node --test tests/local-transaction-v059.test.mjs
node --test tests/*.test.mjs
```

## 設計・安全性の留意点

この試作ではテスト用`resolveSession`が本人を識別する。デモ操作担当者の名前を選ぶことと本人認証は異なる。本番にこのセッション解決器を使わない。受信データから権限を作らず、認証基盤の署名・セッションとDB上の権限を照合する。

`node:sqlite`は試作のための選択であり、本番のSQLite採用を決定するものではない。DBの保存ファイルを端末に置いたまま実顧客データを扱う判断もしない。アクセス権限や監査履歴が失敗すれば金額を変更しないという設計方針を本番でも維持する。
